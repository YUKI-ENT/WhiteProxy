# WhiteListProxy — Codex 実装仕様書

> この文書を Codex に渡し、リポジトリを作成して段階的に実装すること。曖昧な点は安全側（deny by default）に倒し、README とテストで説明する。まず動く最小構成を実装し、機能を段階追加する。途中で仕様に反する近道を採らない。

## 1. 目的と前提

Windows 11 Pro 上で動く、一般ユーザー向けの **日本語GUI付きホワイトリスト型 HTTP/HTTPS 明示プロキシー** を開発する。

用途：インターネットへの直接接続が原則遮断されたローカルVLAN内のPCから、管理者が許可したサービスだけ利用できるようにする。

- Google検索（検索結果を表示。検索結果の外部サイトは原則拒否）
- ChatGPT、Claude
- Google翻訳
- Windows Update（WU）・Defender更新
- 電子カルテ・業務アプリの更新ダウンロード（ユーザー定義サービス）

**最重要機能**：宛先ドメインによるホワイトリスト、接続元端末IP別制御、日時スケジュール（毎日・曜日指定）、管理者が指定する期限付き一時開放（例：Windows Update用に今から90分だけ許可）。期限経過後はGUIが閉じていても自動遮断する。

### 1.1 非目標

- TLS/HTTPSの復号（MITM）、独自ルートCA証明書の配布、HTTPS本文検査をしない。
- Webフィルタ製品相当のURLパス単位制御、マルウェア検査、キャッシュ、ユーザー認証連携、透明/横取りプロキシー、VPN、Windows Update更新プログラム承認機能（WSUS相当）は作らない。
- 直接インターネット接続、アプリ独自の通信、UDP/443 (QUIC)、P2P、DoHなど、**プロキシーを経由しない通信を本アプリ単独で遮断できると約束しない**。対象VLANのルーター/Firewallで出口を制限する必要がある。

## 2. 技術スタック・構成

- 言語 C#、ターゲット .NET 10、Windows 11 Pro x64を主対象。
- UI：Windows Forms、日本語。UIとサービスを完全分離する。
- プロキシー：NuGet **Titanium.Web.Proxy**（埋め込み可能な MIT ライセンスのライブラリ）。最新の公式ドキュメントを必ず確認し、現在のAPIに合わせる。パッケージバージョンを固定し、依存関係とライセンスを記録する。
- サービス：`Microsoft.Extensions.Hosting.WindowsServices` を利用するWindows Service、OS起動時自動開始。
- IPC：ローカル Named Pipe（まずはこれ）。Windows ACL、呼出者認可、リクエスト検証を実装。一般ユーザーから設定変更できないこと。読み取り権限と変更権限を分ける。
- 永続化：`%ProgramData%\WhiteListProxy\` 内のJSON（初期版）。原子的書換え、一世代以上のバックアップ、スキーマバージョンを備える。後でSQLiteへ切替可能なRepository境界を置く。
- ログ：構造化ログ、ローテーション、保持日数設定。UTF-8。生のHTTP本文、認証ヘッダー、Cookie、クエリ値をログに残さない。
- 配布：Windows x64 self-contained publish。GUIとサービスの導入/更新/アンインストールを一貫して行うインストーラーを用意（WiX / Inno Setupなど妥当なもの）。Windows Firewallルールも必要最小限で設定。

## 3. 主要な概念

- **Device**：クライアント端末。IPv4単一アドレスまたはCIDR、表示名、有効/無効。初期版は IPv4 必須、IPv6は明示的に未対応としてUI表示するか正しく追加実装する。IPv4-mapped IPv6を含むアドレス正規化を行い、意図しないアクセスを許さない。全端末一括指定も管理者の明示操作のみ。
- **ServiceDefinition**：Google検索、ChatGPT等の論理サービスとそのホスト許可パターン、TCPポート、表示名。組み込み定義とユーザー定義を区別する。
- **AccessPolicy**：端末または端末グループに対して、サービスをいつ許可するかを定義。必要ならホスト単位で上書き可能にするが、初期版はサービス単位優先。
- **RecurringSchedule**：毎日または曜日別、ローカル時刻の開始/終了、祝日自動解釈なし。複数作成可能。
- **TemporaryGrant**：端末×サービス単位の一時許可。UTC開始/UTC失効、作成者、理由、作成日時、取消状態、IDを保持。
- **ConnectionSession**：接続元IP、宛先ホスト/ポート、利用サービス、開始日時、関連付けられた許可の有効期限、接続ハンドル、転送量。切断管理に使用する。

### 3.1 ポリシー評価規則（曖昧さを残さない）

通信を許可する条件は **すべて** 成立すること：

1. 接続元IPが有効なDeviceに登録されている。
2. 宛先ホストとポートが有効なServiceDefinitionのいずれかに合致する。
3. そのDeviceとServiceDefinitionの組合せに対して、(a) 常時許可、(b) 現在有効なRecurringSchedule、(c) 現在有効なTemporaryGrant のいずれかが存在する。
4. 管理者の明示的なグローバル遮断、端末の一時停止、サービスの無効化、個別の明示拒否に該当しない。

**優先順位**：明示拒否・全遮断・端末無効・サービス無効 ＞ 一時許可/定期許可/常時許可 ＞ デフォルト拒否。未登録端末と未知ドメインは常に拒否。管理用IPCはプロキシーの公開ポートからアクセスできない。

複数ルールが一致するときは許可が継続する最も遅い期限を計算する。ただし明示拒否が常に最優先。一時許可が終わっても有効な定期許可があるなら継続してよい。

## 4. プロキシーの動作（セキュリティ必須）

### 4.1 通信

- 明示HTTPプロキシー（例：サーバーのVLAN側固定IP:3128）。ポートとバインドIPはGUIで変更可能。**デフォルトはループバックにのみバインド**して誤公開を防ぎ、管理者がLANアドレスを選んで有効化する。
- HTTPリクエストとHTTPS `CONNECT host:port` を扱う。HTTPSは単なるトンネルでTLS復号しない。WebSocket、SSE、HTTP Range、長時間ダウンロードを壊さず中継する。
- 宛先ポートは原則 80/443 のみ。サービスごとに追加許可できるがポート無制限設定は危険表示。`CONNECT` の任意ポートへのトンネルを許可しない。
- **通信を開始する前** に、接続元IP/要求ホスト/ポートに基づいてポリシー評価を行い、拒否なら直接接続しない。HTTPなら403、CONNECTは403または適切なプロキシー応答を返す。接続先がポリシー上許可されたホストと一致しないリダイレクト先へ自動的にアクセスしない。
- CONNECT Authority、HTTP absolute-form URI、Hostヘッダーが矛盾するケースは拒否。ユーザー入力・ホスト名は正規化（IDN→ASCII、lowercase、末尾ドット、厳密なサブドメイン境界、IPv6リテラル）。`evilgoogle.com` を `google.com` のサブドメインと判定しない。
- 許可パターンは **完全一致** `example.com` と **サブドメインのみ** `*.example.com` を分ける。`*.example.com` が `example.com` 自身を含むかは **含まない** と定義し、GUIで両方選べるようにする。正規表現の自由入力は初期版では提供しない。
- リテラルIPを指定したHTTPS CONNECT / HTTP Hostへの接続は、サービス側で明示登録したIPのみ許可。ホスト名の名前解決結果がprivate/loopback/link-local/multicast/未指定アドレスなら拒否（管理者が明示的に許可した安全な例外を除く）。DNS rebinding対策として接続直前に解決したアドレスを検査し、その検査済みアドレスへ接続する設計を確認する。
- DNSの名前解決失敗を無条件で許可に変えない。禁止ドメインへのDNSアクセスや接続先変更は不許可。
- 上流HTTPプロキシーの連携は第2段階。まずは直接外部へ到達する構成を作る。
- プロキシー自身が使用する外部ネットワーク、Windows Firewall、LAN境界の要件を文書化する。

### 4.2 接続終了とスケジュール境界

- 既定は **hard cutoff（強制遮断）**。一時許可の失効、スケジュール終了、端末/サービス無効、グローバル遮断が発生したら、そのルールで許可されていた **既存のTCP/CONNECTセッションも終了**させる。ただし別の有効な許可により継続可能なら切断しない。
- 失効時の新規接続は即時拒否。既存接続切断は5秒以内を目標として実装し、実機テストで確認。サービス側に接続セッションの追跡と CancellationToken/ソケット終了経路が必要。
- 大きなWindows Updateのダウンロード途中でも時刻に達したら切断する（既定）。ユーザー向け警告を出し、別モード「新規接続のみ拒否」は将来オプションとしMVPには不要。
- PCのスリープ復帰、Windowsサービス再起動、OS再起動、GUI未起動でも失効を守る。許可判定ごとに現在時刻を見て評価し、周期タイマーだけに依存しない。
- 時刻は保存時UTC、予定表評価は設定されたIANA/Windowsタイムゾーン（デフォルト `Tokyo Standard Time`）で行う。PC時刻の逆行/前進、夏時間、日付変更、サービス再起動への対処とテストを用意する。現在時刻が信頼できない異常を検知した場合は安全側に倒す。

## 5. スケジューリング仕様

### 5.1 定期開放

- `毎日 12:00–13:00`、`月〜金 18:00–20:00`、`土曜 09:00–12:00` 等。
- GUIで曜日チェック（日本語 月火水木金土日）と開始/終了（24h形式）を選ぶ。複数スケジュールを端末×サービスに紐付けできる。
- 日跨ぎ例：`金曜 23:00–土曜 02:00` は **金曜開始の1枠** と定義する。終了が開始より早い場合は翌日扱い。開始と終了が同じ場合はエラー（24時間開放は専用の常時許可）。曜日は「開始曜日」。
- 開始/終了は `[start, end)` の半開区間で、終了時刻ちょうどで失効。
- グローバルON/OFFスケジュールではなく、**端末IP×サービス別** に設定できることを主機能にする。一括適用機能も用意。

### 5.2 一時開放（ワンショット）

- GUIから端末IPを1台・複数台選択 → サービス（例Windows Update）を選択 → `30分/1時間/2時間/4時間/カスタム` → 「開放」を実行。
- 現在時刻からの相対期限と、指定日時までの絶対期限の両方式。開始予約も可能にする（MVPでは今すぐ開放と指定日時終了を優先）。
- 画面に **開始・失効日時、残り時間、端末、サービス、理由** を明示。延長・即時終了の操作。残り時間はGUI表示上の補助にすぎず、判定はサービス側で行う。
- 有効期間の上限：既定4時間。管理者が最大24時間まで変更可能。期限なしの一時開放は禁止。
- 失効したTemporaryGrantは監査記録として残す。プロキシーサービス再起動後に失効済みのものが復活してはならない。
- 同じ端末×サービスに一時開放を重複作成する場合、GUIから「既存の期限を延長」か「別の許可を追加」を明確に選択させる。MVPでは重複を避けて「延長」に統一してよい。
- 「Windows Updateを1回だけ」＝ **更新処理の完了検出ではなく、指定した1つの時間枠だけ開放** を意味する。更新完了を自動判定して閉じる仕組みはMVP対象外。ラベルや説明に明記。

### 5.3 GUI切断・障害時

- GUIが閉じてもスケジュール・TemporaryGrantはWindowsサービス単独で動作する。
- ポリシー保存/読取に失敗した場合は新規接続を拒否。稼働中の許可判定に異常があれば強制切断し、監査ログに残す。
- IPC切断がプロキシーの停止原因にならない。

## 6. GUI画面設計（日本語・初心者向け）

### 6.1 ダッシュボード

- プロキシー状態（稼働中/停止中/エラー）、待受IP:ポート、接続中端末数、現在許可中サービス、直近の拒否数。
- 大きなボタン：「一時開放」「すべて遮断」「端末管理」「許可サービス」「スケジュール」「通信ログ」「設定」。
- 「現在開放中」一覧：端末名/IP、サービス、開放理由、終了時刻、残り時間、即時終了ボタン。
- 「すべて遮断」は確認ダイアログ付きで新規/既存通信を遮断。自動スケジュールより優先し、解除は管理者操作のみ。

### 6.2 端末管理

- IP、表示名、グループ、無効化、最終接続日時、現在の許可サービス。
- IPv4単一IPとCIDRを登録可。IP重複やCIDRの重なりを警告。ネットワークを跨ぐ誤登録は確認。
- 検出された未知端末をログ上で表示しても **自動許可しない**。

### 6.3 サービス管理

- 組込みテンプレート：Google検索、ChatGPT、Claude、Google翻訳、Windows Update、Microsoft Defender、電子カルテ更新（後者は空のユーザー定義テンプレート）。
- ホストパターン/ポート一覧の表示、編集、コピー、新規追加。有効/無効。
- **テンプレートは初期候補であり、完全な接続先リストを保証しない**。ベンダー公式の公開資料を調べて出典・確認日・定義バージョンを記載する。推測したCDNを勝手に広く許可しない。
- WU と Defenderのホストが重複する可能性、Googleドメインが検索以外の機能も提供する点をGUIに注意表示。
- 接続拒否ログから候補ドメインを選択しサービスに追加可能。ただし手動確認・注意表示・権限チェックを必須にする。

### 6.4 スケジュール管理

- 対象端末、対象サービス、曜日チェック、開始/終了時刻、ルールの有効/無効、今週の次回実行予定を表示。
- 夜間跨ぎ・複数ルールの重なり・時刻変更の結果をプレビュー。

### 6.5 通信ログ

- 時刻、端末IP/名前、宛先ホスト、ポート、許可/拒否、理由（例：未登録端末・未許可ドメイン・時間外・手動遮断・接続エラー）、転送量、継続時間。
- フィルタ：端末/サービス/許可拒否/期間、検索、CSVエクスポート、ログ保持日数。
- プライバシーを考え、URLのクエリ文字列、リクエスト本文、ヘッダー中のCookie/認証情報を保存しない。監査ログは設定変更/一時開放/解除を必ず記録。

### 6.6 その他

- メインの操作は日本語。アイコン+文字を使い、赤緑の色だけに依存しない。
- ヘルプに「プロキシーを設定していないPCには効果がない」「同じホスト内のURLは区別できない」「Microsoft更新は一部直通が必要な場合がある」などを説明。
- GUIはサービスが停止していても接続状態を表示し、修復手順を示す。

## 8. Windows Updateとプロキシーの現実的な制約

- Windows UpdateはWinHTTP、BITS、Delivery Optimization（DO）等を使い、通常ブラウザーとプロキシー利用方法が異なる。単に `netsh winhttp set proxy` を実行するだけで全通信が対象になると想定しない。
- MicrosoftのDO資料では、特定のDOサービス接続先には直接アクセスが推奨されるなどの制約がある。したがって **「WUだけ開放すれば必ず更新成功」や「プロキシーだけで全WUを完全遮断」とは謳わない**。
- `Range` / `Content-Range` / `Accept-Ranges` やHTTP 206 Partial Content、並列ダウンロード、再試行を破壊しない。
- クライアントの設定方法はGPO/端末全体のプロキシー、WinHTTP/WinINET/DOの差異を検証した上で `docs/client-setup.md` に記載。CLIの `netsh winhttp` だけを唯一の設定手段として推奨しない。
- 更新を確実に時間制御する環境では、VLAN境界FWによる直接外部接続禁止と、必要な例外の設計が不可欠。
- 初期実装に、配信の最適化のP2P制御や更新完了確認は含めない。

## 9. 運用・セキュリティ

- Open Proxy化防止：初期listenは127.0.0.1、接続元IPはホワイトリスト登録必須、外部インターフェイスに公開しない。Windows Firewallで管理VLAN/指定送信元IPに限定。IPv6待受はデフォルト無効。
- 複数NIC対応：GUIから待受IPを明示選択。`0.0.0.0` 選択時は危険確認ダイアログ。IPv4送信元はTCPソケットの実際のPeer IPを使用し、`X-Forwarded-For` 等を信頼しない。
- 設定ディレクトリは管理者とサービス専用IDにのみ書込権限。サービスを可能な限り低権限で動かす。不要な管理者権限常駐は避ける。
- IPCはローカルに限定し、Windowsセキュリティ識別子/ACLで管理者以外から設定変更不可にする。ポリシー変更イベントには操作者と日時を記録。
- 過負荷対策：最大同時接続数、タイムアウト、帯域/ログ量制限、メモリリーク対策、キャンセル伝播。巨大レスポンスをメモリに全読み込みしない。ストリーミング転送を使う。
- 設定の「編集」「検証」「適用」を分け、検証エラーなら元の設定を保持。適用失敗時は明確なアラームとrollback。読込失敗は安全側。
- サービス再起動後の接続切断、設定破損、電源断、時計変更でも権限昇格や意図しない開放が起きないこと。
- 通信量を抑えるためロギングは非同期とし、キュー溢れ時の動作を定義する。監査ログは欠損を可視化する。
- 患者情報や業務機密の外部AIサービス送信を、プロキシーが安全化するものではない。利用ポリシーは別途必要。

## 10. 実装手順（Codexはこの順番で進める）

### Phase 0 — API調査と技術検証

1. 最新の公式Titanium.Web.Proxy API、ライセンス、MITMなしのExplicitProxyEndpoint、CONNECT許可前判定、長時間接続の終了手段を確認。
2. まず最小コンソールアプリでHTTP/HTTPS CONNECTの成功と拒否を検証。
3. **最重要：Active CONNECTを時刻失効時に強制切断可能か実証**。Titanium APIでできなければ、ライブラリの抽象化・セッション管理の工夫を検討し、それでも難しければMVPでごまかさず報告する。場合により実績ある他のプロキシーエンジン、または最小のCONNECT専用転送層の採用を設計判断として記録。
4. HTTP Range/206、WebSocketと長時間接続を確認。
5. 調査結果を `docs/architecture.md` に整理し、技術的な制限を明示。

### Phase 1 — 安全なプロキシー本体

1. Solutionとテストプロジェクトを作成。
2. Coreに接続元IP、宛先ホスト、ポート、サービス、ポリシーの判定エンジンを作る（エンジンにネットワークアクセスを持たせない）。
3. TitaniumアダプターでACL許可/拒否を行う。TLS復号OFF。
4. Windowsサービス化、最小限のJSON設定、構造化ログ。
5. 未登録IP/ホスト拒否、IP偽装不能、誤ったHost、ローカル宛て不正接続をテスト。

### Phase 2 — 時間制御

1. Coreに定期予定表と一時許可の評価器を実装。
2. サービス再起動/GUI終了を跨ぐ期限管理とセッション強制切断を実装。
3. 時計は `TimeProvider` を注入し、テスト内で仮想時刻を進められるようにする。
4. 境界時刻、日跨ぎ、曜日切替、複数許可・優先順位、取消/延長をテスト。

### Phase 3 — 管理GUI

1. ダッシュボード、端末管理、サービス管理、スケジュール、一時開放、ログ画面。
2. Named Pipe IPCと管理者認可。設定のプレビュー・検証・保存・反映。
3. 簡単なヘルプとクライアント設定手順。

### Phase 4 — Windows Update 実機検証と配布

1. 実PCで Windows Update の確認とダウンロード、Defender定義更新、一般ブラウザー、ChatGPT、Claude、Google検索、Google翻訳、電子カルテ更新用HTTP/HTTPSサンプルを検証。
2. 認証/関連CDN/リダイレクトなど必要宛先を記録し、保守可能なサービス定義を作成。
3. インストーラー、自己完結配布、アップグレード、設定移行、アンインストール、Windows Firewall管理、ログ収集を整備。
4. 操作説明書を一般ユーザー向けに仕上げる。

## 11. 必須テストケース（自動化を優先）

1. 未登録端末は常に拒否。
2. ホワイトリスト外ホストはHTTPS CONNECTでもHTTPでも拒否。
3. `*.example.com` は `a.example.com` に一致、`example.com` と `evil-example.com` に一致しない。
4. `example.com.evil.test` や大文字、末尾ドット、IDN、IPリテラルで許可のすり抜けがない。
5. `CONNECT allowed.example:22` はポートが未許可なら拒否。
6. 月〜金12:00-13:00設定で月曜11:59:59拒否、12:00:00許可、13:00:00拒否。
7. 金曜23:00〜土曜02:00は日付が変わっても正しく許可し、土曜02:00に遮断。
8. 90分の一時許可は開始後89分で許可、90分で拒否。GUIを閉じ、サービス再起動しても期限を超えて許可しない。
9. 一時許可期限中にダウンロードまたはWebSocket接続を維持し、失効後に既存セッションが終了する。
10. 定期許可と一時許可が重なる場合、一方の期限終了時に他方が有効なら継続。
11. 端末無効化/サービス無効化/全遮断で既存接続が終了。
12. 不正な設定ファイルでは意図しない許可が発生しない。復旧/通知動作が確認できる。
13. ログにCookie、Authorization、検索キーワード、本文が含まれない。
14. HTTP 206 Rangeや複数GB相当のストリーミング（テスト用模擬サーバー）が正常。
15. UIの一般ユーザーから設定変更IPCが拒否され、管理者は変更できる。
16. LAN待受やWindows Firewallの状態が意図せず全ネットワークへ開かれない。
17. 休日/夏時間のあるタイムゾーンやPC時計変更でも仕様どおり失効（時刻異常時は安全側）。
18. IPアドレスが一致しても未知ホスト、DNS rebinding、private IP宛への踏み台化が防止される。

## 12. 完了条件

- 管理者がWindows上のGUIだけで、端末・サービス・日時と時間制限を設定できる。
- GUI未起動でもサービスが動き、時間切れになると**新規・既存の許可対象通信が適切に遮断**される。
- ドメイン単位のホワイトリストが有効で、TLS復号を行わずHTTP/HTTPS通信を処理する。
- 未登録端末にサービスを公開せず、誤設定時に意図せず全開放しない。
- 自動テストが通り、ビルド・サービス導入・クライアント設定・検証手順がREADMEにある。
- WUでプロキシーを経由できない通信の制約が、ユーザー向けドキュメントに明記されている。

## 13. Codexへの作業上の指示

- まずPhase 0の技術検証をし、結果を報告してから、可能な範囲でPhase 1以降を実装。途中で実装不能な箇所があれば、理由・代替策・残課題を明示する。
- コード例ではなく **ビルド・実行できる実コード、ソリューション、テスト、README** を作成する。
- Windows依存のAPIはインターフェイス化し、Linux CIなどでもCoreテストが走るようにする。
- 外部入力はすべて検証、例外は監査可能なログ、通信許可はfail-closed。特に時間切れの既存接続終了を省略しない。
- ネットワーク接続先一覧は製品ごとのテンプレートデータとして管理し、根拠不明の大量のワイルドカード許可をしない。
- 変更ごとに `dotnet build`、`dotnet test` を実行し、失敗内容を報告。手元環境がWindowsでない場合はWindows実機未検証として明記する。
- コードは読みやすく、必要箇所には日本語コメントを入れる。複雑な仕組みを増やしすぎず、MVP完成を優先する。
